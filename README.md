# /0byte/ — Zero Server Peer Messaging (0SPM)

A browser-based, peer-to-peer encrypted messenger that requires no server for message exchange. All data, including keys and history, stays on the device.

## How it works

Two peers establish a direct WebRTC connection. A shared symmetric key is generated for each chat and exchanged over the data channel. Messages are encrypted with AES-256-GCM before sending. Fingerprints derived from the SDP are displayed as mnemonic words for manual verification against MITM attacks.

## Core features

- **No server**: Connection is established via STUN (Google's public servers by default), no TURN, no relay, no storage server.
- **E2E encryption**: AES-256-GCM with random keys per chat. Keys never leave the device unencrypted.
- **Master password (optional)**: Protects local data (contacts, history) with PBKDF2-derived AES-256-GCM. Salt is stored in localStorage.
- **QR code exchange**: SDP payloads can be encoded as QR codes and scanned from screenshots to simplify the handshake.
- **Image sharing**: Compressed JPEG, encrypted before transmission.
- **Fingerprint verification**: Three-word mnemonic codes derived from SDP fingerprints must match on both sides to confirm the channel.
- **Session restoration**: Chat roles (host/guest) and keys are persisted, allowing reconnection without re-verification if the fingerprint was previously confirmed.
- **Theme support**: Dark and light modes via CSS custom properties.
- **No accounts, no metadata leakage**: Identity is a randomly generated `uid` stored locally.

## Data model
contacts = {
<peerId>: {
name: string,
avatar: string,
localSessionKey: hex(32 bytes),
remoteKey: hex(32 bytes),
role: "host" | "guest"
}
}

history = Array<{
type: "message" | "image",
from: uid,
ciphertext: base64(iv + AES-GCM),
mimeType?: string,
timestamp: number
}>

- `localSessionKey` is the AES-256 key generated by this peer.
- `remoteKey` is received from the other peer over the data channel.
- History is stored per pair: `history_{sorted(uid1, uid2)}_joined`.
- All local data is either stored as plain JSON in `localStorage` or encrypted with the master password.

## Connection flow

1. **Host** creates an offer, generates a room ID and AES key. The SDP is packed into a JSON payload and shared (copy-paste or QR).
2. **Guest** pastes the offer, creates an answer. The SDP answer is returned to the host.
3. Both sides display a three-word fingerprint. Users must confirm the match.
4. After confirmation, AES keys are exchanged over the data channel.
5. All subsequent messages are encrypted with these keys.

## File structure
index.html - SPA with all UI markup
style.css - Styling, themes, responsive layout
crypto.js - CryptoSystem class: AES-256-GCM, PBKDF2, SHA-256 helpers
webrtc.js - WebRTC setup, QR generation/scanning, key exchange, session restore
ui.js - DOM manipulation, chat rendering, settings, modals
app.js - Entry point, event binding, initialisation

## Dependencies

- `qrcode-generator` (v1.4.4) - QR code rendering.
- `jsQR` (v1.4.0) - QR code reading from images.

All loaded via CDN, no build step required.

## Limitations

- No TURN server configured; connection may fail behind symmetric NATs.
- No offline message delivery.
- History is stored in localStorage and may be cleared by the browser.
- Master password cannot be recovered; data is lost if forgotten.

## Usage

1. Open the HTML file in a browser (no web server needed).
2. Optional: set a master password to encrypt data at rest.
3. Create a chat (Host) or join one (Guest) by exchanging invitation codes/QRs.
4. Verify the three-word fingerprint with the peer.
5. Communicate.
